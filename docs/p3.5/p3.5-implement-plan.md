## S2：控制面板细节优化（SPA 改造，纯前端 + 调 S1 新端点）

**改 `server/app/dist/index.html`**（保持单文件 + 原生 fetch）：

### 2.1 蒸馏任务列表视图（issue「控制面板」第 1 项）
- 新增「蒸馏任务」卡：调 `GET /api/jobs` 渲染列表（job_id / status badge / phase / 耗时从 started_at↔finished_at 算 / 产物数）
- 取代当前只轮询单 job 的 `distill-out` 区：提交蒸馏后高亮新 job 行 + 该行实时轮询；历史 job 保留可点
- 耗时计算：`done/failed` 用 `finished_at - started_at`；`running` 用 `now - started_at`（每秒随轮询刷新）

### 2.2 蒸馏进度条可视化（issue 第 2 项）
- 当前 job 行加进度条：`current/total` 渲染为 `<progress>` 或 div 宽度；phase 文本旁边
- failed 时整行高亮（红边 + error tooltip）；done 时绿边
- `total=0`（如 ATOMIZE/CLASSIFY 阶段无 total）显示 indeterminate 状态（脉冲动画），不显示百分比

### 2.3 产物浏览树（issue 第 3 项）
- 「蒸馏产物」卡改造：点 host → 展开 md 文件列表（调 `GET /api/skills/<host>/files`）→ 点文件 → 内联预览内容（调 S1 1.4 端点，`<pre>` 渲染）
- 「采集产物」卡同理：点 capture 名 → 展开详情（调 S1 1.2，显示 events 数 / stages / host）+ 「用此 trace 蒸馏」按钮（填入蒸馏表单的 trace_path）

### 2.4 录制状态实时刷新（issue 第 4 项）
- 当前 `/api/status` 每 3s 刷新；S1 已加 session 字段，状态卡补展示：session_id（短）/ 已采事件数 / 当前 stage / host
- 录制中时状态卡高亮（running badge + 边框），非录制时灰色

### 2.5 从最近 capture 选 trace（issue 第 5 项）
- 蒸馏表单 trace_path 输入框旁加下拉 `<select>`：选项来自 `GET /api/captures`，值为 `<trace_path>` 全路径，选中即填入输入框
- 与 2.3 的「用此 trace 蒸馏」按钮互补（下拉适合多选场景，按钮适合浏览时直接触发）

### 2.6 错误/通知反馈（issue 第 6 项）
- 加轻量 toast：固定顶部，`showToast(msg, type)` 函数（success/error/info），3s 自动消失
- 替换当前所有 `alert(...)`（蒸馏触发、trace 未填等）
- 蒸馏失败时 toast 红色 + 详情

### 2.7 响应式与暗色模式打磨（issue 第 7 项）
- 现有 `prefers-color-scheme` 已覆盖亮/暗；补：窄屏（<640px）`<select>`/进度条/卡片 grid 自适应（flex-wrap 已有，确认无横向溢出）

### S2 验证

## S3：配置功能增强（后端自检端点 + 前端配置表单）

### 3.1 `GET /api/config/check`（issue「配置增强」第 2 项 —— LLM 连通性自检）
**改 `server/server.py`**：新端点，调 `call_llm_fast` 发一个最小 prompt（如 `"ping"`，`max_tokens=8`，`timeout=20`）：
```python
@app.get("/api/config/check")
async def config_check() -> JSONResponse:
    if not config.LLM_KEY:
        return {"ok": False, "error": "LLM_KEY 未配置"}
    try:
        text, usage = await asyncio.to_thread(
            call_llm_fast, "ping", max_tokens=8
        )
        return {"ok": True, "model": config.CLASSIFY_MODEL, "reply_len": len(text), "usage": usage}
    except Exception as e:
        return {"ok": False, "model": config.CLASSIFY_MODEL, "error": str(e)}
```
- 用 `asyncio.to_thread` 包（LLM 是同步 urllib，不阻塞事件循环，对齐 distill_api 模式）
- 用 `call_llm_fast`（CLASSIFY_MODEL，短超时），不是 `call_llm`（贵）
- **注意**：自检真发网络请求，但这是用户在控制面板**主动点「自检」触发**的，不是自动化测试 —— 测试用例要 mock `call_llm_fast`，不真发

### 3.2 配置编辑表单（issue「配置增强」第 1、3 项）
**改 SPA**：
- 「当前配置」卡改造：从只读 `<pre>` 改成分组表单（对齐 `_CONFIG_WRITABLE` 4 个 key）：
  - **模型参数**：DISTILL_MODEL / CLASSIFY_MODEL / LLM_BASE / LLM_TIMEOUT
  - 其余字段（llm_key_set/llm_insecure/output_dir/min_bucket_size）只读展示（不在白名单，不可写）
- 每个可写字段一个 input，值预填当前 `config.describe()`；「保存」按钮 → `POST /api/config {values: {...}}`
- 表单校验：LLM_TIMEOUT 必须是正整数（前端校验，失败 toast 不发请求）
- 保存成功后 toast + 重新拉 `/api/config` 刷新展示

### 3.3 LLM 自检按钮（issue「配置增强」第 2 项）
- 配置卡加「LLM 自检」按钮 → 调 `GET /api/config/check` → 成功 toast 绿（显示 model + reply_len）、失败 toast 红（显示 error）
- 按钮点击时 disabled + 「自检中…」，防重复点

### 3.4 配置项分组（issue 第 3 项）
- 3.2 表单已按「模型参数 / 路径 / 管线参数」分组渲染（对齐 `config.describe()` 字段语义）
- 不可写的字段（output_dir/min_bucket_size）展示在「路径」「管线参数」组下，标灰「只读（改 .env）」

### 3.5 输出目录可视化跟随（issue 第 4 项）
- 改 OUTPUT_DIR 实际通过改 `.env` 的 OUTPUT_DIR 行 —— 但当前 `_CONFIG_WRITABLE` 不含 OUTPUT_DIR
- **决策**：P3.5 **暂不加 OUTPUT_DIR 进白名单**（改输出目录是较高风险操作，路径错会丢产物），只在配置表单里**只读展示** output_dir，并在「蒸馏产物」卡顶部显示当前 skills_dir 路径（让用户知道看的是哪个目录）。真正可写 OUTPUT_DIR 留后续。
  - 这条 issue checkbox 标注「部分实现（只读展示，可写留后续）」

### S3 测试（`tests/test_serve.py` 增量）
- `test_config_check_no_key_returns_error`：mock config.LLM_KEY='' → `/api/config/check` 返 `{ok:false, error:"LLM_KEY 未配置"}`
- `test_config_check_success`：mock `call_llm_fast` 返 `("pong", {"in":1})` → 返 `{ok:true, model, reply_len:4}`
- `test_config_check_failure`：mock `call_llm_fast` 抛异常 → 返 `{ok:false, error}`（不 500，对齐 3.1 设计）
