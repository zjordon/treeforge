# P2.3.2 扩展补全实施方案（数据驱动聚焦版）

> 本文档是 P2.3.2 的实施方案，待用户审阅批准后执行。
> 起因：上下文恢复后从 `docs/p2/handoff.md` 继续工作，用户选择从 P2.3.2 开始。
> 本方案**推翻了 handoff 清单的部分优先级**——依据是 `data/captures/` 两份真机录制数据的实测结果。

## 一、数据驱动的优先级重排

检查 `data/captures/72111447` 和 `0ddbaa84` 两份真机 bilibili 投稿录制，结论如下：

| handoff 清单项 | 实测结果 | 决策 |
|---|---|---|
| IME（composition）完善 | ✅ **已正常工作**：中文合成值（`browser-use体验及wvs`、`ai浏览器第5期-browser-use`）正确采集 | ❌ 不做 |
| contenteditable MutationObserver | ✅ **已能采集**：简介 `<div contenteditable=true>` 的 innerText 正常入 trace | ❌ 不做 |
| scroll 去抖优化 | scroll 事件虽无 target，但不影响蒸馏质量 | ❌ 不做 |
| extractor 注册表 | 为 replay 策略铺路，当前 replay 未做 | ❌ 不做（过早抽象） |
| **输入碎片化**（handoff 低优先级） | ❗ **真痛点**：标题字段一次输入被切成 **5 个 input 事件** | ✅ 升为核心 |
| contenteditable 语义缺失（handoff 未列） | ❗ **真痛点**：点简介渲染成 `div contenteditable=true :: div`，无法区分 | ✅ 升为核心 |

**核心洞察**：handoff 清单按「理论上的完整性」列项，但实测数据表明其中两项（IME、MutationObserver）已经能用，真正的痛点是另外两项。本方案按数据驱动重排优先级。

## 二、改动详情

### 改动 1（核心）：atomizer 输入合并 — `harness/atomizer.py`

在 `_filter_noise` 新增第 4 类去噪：**连续同目标 input 合并**，保留终值。

**逻辑**（对齐现有 click 合并模式，atomizer.py:112-121）：
- 当前 event 是 `input`，且 `out` 末尾也是 `input`
- 同一目标：`element_attrs` 稳定标识匹配（`id`/`name`/`placeholder`/`aria-label`/`aria-labelledby` 任一相同；都无标识则同 tag），**或** selector 相同（老格式兜底）
- 同一 url
- 间隔 < 30s（比 click 的 2s 宽——真实打字停顿可达数秒）
- 合并方式：用后者覆盖前者（保留终值 value + 终值 timestamp）

**为什么放 atomizer 而不是扩展端**：
扩展端 debounce（400ms）对快打字已生效，但无法预测人类停顿（实测 630ms–3778ms）。任何合理的 debounce 窗口（如 2000ms）都有风险误合并无关连续输入或丢失用户有意停顿的轨道。后端 `_filter_noise` 的合并是确定性的、无副作用的「同目标连续输入只看终值」语义，与现有 click 合并对称，是确定性兜底。

**新增测试** `tests/test_atomizer.py`：
- `test_filter_noise_merges_consecutive_inputs_same_target`：同 placeholder 连续 5 个 input（模拟真机标题场景）→ 合并成 1 个，value 是终值
- `test_filter_noise_keeps_inputs_different_target`：切换目标（标题→标签）→ 保留各自
- `test_filter_noise_keeps_inputs_over_30s`：间隔 > 30s → 不合并
- `test_filter_noise_input_merge_preserves_final_value`：值序列 `'ai' → 'aib' → 'aic'` → 终值 `'aic'`

### 改动 2：contenteditable 上下文语义标签 — `extension/src/strategies/distill/index.ts`

`computeTargetLabel` 增强：当目标是 `[contenteditable]` 时，补抓语义提示，让点击简介不再只是 `div contenteditable=true`。

按优先级（WAI-ARIA 标准关联 + DOM 启发式）：
1. `aria-label`（已采，但 contenteditable 常没有）
2. `aria-labelledby` 指向的元素文本（bilibili 简介上方有 `<h3>简介</h3>`）
3. 邻近的前序标题元素（向上找最近可交互祖先内，查 `<h1>-<h6>` / `<label>` / `[data-label]`）
4. 兜底 `contenteditable`（当前行为）

同时让 `extractRawAttrs` 采 `aria-labelledby`，需同步双端契约（见改动 2b）。

**收益**：点简介后 summary 变成 `div contenteditable=true aria-labelledby=xxx :: 简介`，LLM 能识别这是「简介输入框」而非无名 div。

### 改动 2b：双端契约同步加 `aria-labelledby`

| 文件 | 改动 |
|---|---|
| `extension/src/shared/distill-schema.ts` | `RAW_ATTR_KEYS` 加 `aria-labelledby` |
| `treeforge/capture/distill_schema.py` | `RAW_ATTR_KEYS` + `ELEMENT_ATTR_WHITELIST` 加 `aria-labelledby` |
| `harness/atomizer.py` | `_ATTR_WHITELIST` 加 `aria-labelledby` |

**契约测试**：`tests/test_distill_schema.py` 的 `test_raw_attr_keys_cover_whitelist` 和 `test_whitelist_superset_of_atomizer` 会自动覆盖新 key；额外加一个 contenteditable + aria-labelledby 的提取测试。

### 改动 3（兜底）：扩展端 input 合并窗口调优 — `extension/src/strategies/distill/index.ts`

`INPUT_COALESCE_MS`: 400 → **1200ms**。

**理由**：400ms 对人类正常打字停顿太短（实测真实停顿 630ms 起）。1200ms 能合并大部分连续打字，又不会误合并用户有意停顿后切换的操作（onInput 的 target-switch flush 会先冲刷前一个）。这是预防性兜底，主要修复仍靠 atomizer（改动 1）。

**无测试**：扩展端无测试基础设施（WXT 项目无 jest/vitest），手动验证。

## 六、风险与回退

- **input 合并的 30s 窗口**：若两个不同字段的 stable-attr 恰好相同（罕见），可能误合并。回退：调小窗口或要求更严格的标识匹配。
- **`aria-labelledby` 解析**：需 `document.getElementById` 查引用元素，content script 隔离世界能访问 DOM（ISOLATED 世界可读），无跨域问题。
- **双端契约**：必须同步改 TS + Python，否则 collector 会过滤掉未在 `RAW_ATTR_KEYS` 的新 key。改动 2b 已列出全部同步点。
